# 2026-09-11

## 从零构建「冰火双人行」（类森林冰火人双人解谜平台游戏）

- 需求：TypeScript + Vite，双人同屏解谜平台，可直接部署 GitHub Pages。
- 技术选型：放弃 Phaser 3，改用**原生 Canvas 2D + 自研离散 AABB 物理**。
  理由：推箱 / 移动平台带骑乘 / 闸门 / 按角色区分的元素免疫都需要确定性自定义解算，
  Phaser Arcade 在移动平台场景有已知抖动；自研后物理层是纯函数，可以做真单测。
- 素材全部程序化生成：`scripts/gen-assets.mjs` + 自研 PNG 编码器（`scripts/lib/pixel.mjs`）
  与 WAV 合成器（`scripts/lib/audio.mjs`），原创 CC0，避免第三方许可问题。

### 已实现
- 5 关 ASCII 关卡数据（`src/game/levels.ts`，40x20 格）
- 机关：拉杆（边缘触发，状态保持）、按钮（持续触发）、闸门、横向平台、升降台、可推木箱
- 元素地形：火池 / 水池 / 酸池，按角色免疫或致死；死亡 0.85s 自动复位
- 评分（通关/全宝石/限时 → 1~3 星）、localStorage 存档、解锁链
- DOM 浮层 UI：主菜单 / 选关 / HUD / 暂停 / 设置（音量）/ 结算
- `.github/workflows/deploy.yml` + `vite.config.ts` 自动推导 GitHub Pages base
- 36 个 Vitest 单测 + `pnpm verify:levels` 关卡体检脚本

### 环境坑（Windows）
- 系统无 pnpm → `npm i -g pnpm`（装到 12.3.4）
- pnpm 10+/12 默认禁止依赖构建脚本，esbuild 会报 ERR_PNPM_IGNORED_BUILDS。
  只有 CLI 传 `--config.dangerously-allow-all-builds=true` 才生效，写进 `.npmrc` 无效。
- Windows 无开发者模式时 pnpm 建软链接失败 → 追加 `--config.node-linker=hoisted`。
- pnpm 12 不再读 package.json 的 `pnpm.onlyBuiltDependencies`。
- **`node-linker` / `allowBuilds` 必须写在 `pnpm-workspace.yaml`（pnpm 12 不读 .npmrc 的
  node-linker）**，用 `nodeLinker: hoisted` + `allowBuilds: {esbuild: true}`。
  命令行等价：`--config.node-linker=hoisted --config.dangerously-allow-all-builds=true`
- jsdom 在这台机器上 pnpm 安装会卡死（87 包链接 30 分钟未完成），已放弃；
  改用不依赖 DOM 的端到端 AI 通关测试，效果更好。
### GitHub Actions 踩坑（重要）
- 旧版 Actions（`actions/checkout@v4`、`actions/setup-node@v4`、
  **`actions/upload-pages-artifact@v3`**）目标 Node 20，在新 runner 上被强制跑在 Node 24
  → **会直接失败**。必须升到 `checkout@v5` / `setup-node@v5` / `upload-pages-artifact@v4`。
- `pnpm/action-setup` 要锁**精确版本**（本项目 `12.3.4`），否则 minor 差异会让
  `--frozen-lockfile` 或 `dangerously-allow-all-builds` 行为不一致。
- install 写成 `pnpm install --frozen-lockfile --config.dangerously-allow-all-builds=true
  || pnpm install --frozen-lockfile` 双保险。
- **2026-09 各 Pages 相关 action 的最新大版本**（写 workflow 时务必查，别凭记忆）：
  `actions/checkout@v7`、`actions/setup-node@v7`、`actions/configure-pages@v6`、
  `actions/upload-pages-artifact@v5`、`actions/deploy-pages@v5`。
  我最初写的 v4/v5 全是 Node 20 时代产物，在 Node 24 runner 上失败。
  查版本：`curl/浏览器打开 https://api.github.com/repos/<owner>/<repo>/releases/latest`
  看 `tag_name`。
- **终极坑：`pnpm/action-setup@v4` 目标 Node 20，在 Node 24 runner 上会失败**，
  导致 pnpm 根本没装上 → 后续所有 `run:` 步骤 exit 1（但日志只显示一句
  "Process completed with exit code 1"，极易误判）。
  解决：**不要用这个 action**，改用 `npm install -g pnpm@12.3.4`（在 setup-node 之后）。
- **本机复现 CI 的可靠做法**：`git archive HEAD | tar -x -C /d/_citest`，
  在干净副本里依次跑 install / typecheck / test / verify:levels / build。
  注意 git archive 出来已是 LF，与 CI 一致；`grep -c $'\r'` 在这个 shell 里是误报，
  判断行尾要用 node `buf.includes(0x0d)`。
- 排查 workflow 时先 `python -c "import yaml;yaml.safe_load(...)"` 验证 YAML 再推。
- workflow 结构建议：test / build / deploy 三个 job，`deploy` 只 `needs: build`，
  这样测试环境问题不会挡住部署，且失败归属清晰。
- 远端 9f82503 的实际失败发生在 **Install dependencies**，test/build 都在同一步失败，
  不是 typecheck/test/build 代码错误；公开 Actions 页面不展示详细日志。
- 最终 CI 改为完全使用 **npm install + npm scripts**，移除 pnpm/action-setup 与 pnpm 安装阶段。
  本地干净副本验证：`npm install`、`npm run typecheck`、`npm test -- --run`（39 passed）、
  `npm run build` 全部通过。
- 排查 workflow 时先 `python -c "import yaml;yaml.safe_load(...)"` 验证 YAML 再推。

- **可用系统 Chrome 跑 headless 截图**：`chrome --headless=new --disable-gpu --no-sandbox
  --window-size=960,560 --virtual-time-budget=5000 --user-data-dir=D:\\_shots\\p
  --screenshot=D:\\_shots\\out.png URL`。
  Windows 路径用 `D:\\path`，反斜杠要双转义。
- 本沙箱里 `rm -rf` / 清空 dist 会被 safe-delete shim 拦截，构建时若 dist 已存在
  需加 `--emptyOutDir=false`。遗留了 `D:\_scratch_bhy/` 目录需要用户手动删除。

### 约定
- 关卡 ASCII：`F/W` 出生点、`D/d` 门、`r/b` 宝石、`o` 箱子都写在"所处的空气格"，
  脚底 = `(row + 1) * TILE_SIZE`。
- 跳跃参数：jumpVelocity -640 / gravity 1800 → 跳高 113.8px（3.5 格）、
  水平 156px（≈4.9 格）。所以 5 格坑过不去、5 格墙跳不上，关卡机关据此设计。
